Coeus AI

A native C++ project-aware AI desktop workspace for working with software projects. Coeus AI combines a custom Skia/SDL2 GUI, local project context, source-grounded retrieval, a policy-first compiled-turn runtime, tool/workflow execution, structured telemetry, and a private headless evaluation harness used to test repository-grounded behaviour.

What this is

Coeus AI was built around the idea that an assistant should understand the currently loaded project, not just answer as a generic chatbot. The app is designed to work against local software projects, inspect project context, retrieve relevant source files, answer repository-aware engineering questions, compare files semantically, and preserve context across follow-up turns.

The goal is not simply to wrap a model in a chat window. Coeus AI explores the application/runtime layer around AI-assisted software work: project state, retrieval, context assembly, tool-style operations, workflow routing, validation, telemetry, and repeatable evaluation.

Internally, the system is organized around a policy-first compiled-turn architecture. A user turn is converted into canonical turn state before retrieval, prompt packing, execution, validation, and telemetry export consume it.

Why it matters

A common failure mode in AI coding tools is that they sound confident while losing repository context, hallucinating unsupported features, or routing normal codebase questions into the wrong workflow. Coeus AI explores a more structured approach to project-aware assistance.

  • Separate local project inventory from proof-bearing source evidence.
  • Assemble answer context from actual project files.
  • Route different user intents through different workflows.
  • Distinguish semantic repository questions from patch/diff requests.
  • Retain useful context across follow-up turns without treating continuity as proof.
  • Identify absent features without hallucinating implementation.
  • Suppress internal trace/vector/project-storage details from user-facing answers.

Architecture summary

Coeus AI is structured as a native desktop AI workspace with a modular runtime core. The architecture separates the GUI, compiled turn state, project context, retrieval, tools/workflows, provider integration, validation, telemetry, and headless evaluation.

Headless evaluation surface

Project context and retrieval

Validation and telemetry

Structured markers, traces, run bundles, answer post-processing, and validation rules support debugging, route analysis, artifact suppression, and private eval reporting.

Context Lattice Engine

The Context Lattice Engine is the runtime idea behind Coeus: every user turn is compiled into a traceable unit before the model is asked to answer.

Design principle

Coeus does not treat retrieval as the owner of truth. Retrieval is one input into a compiled-turn pipeline. The engine keeps policy truth, retrieval truth, packed prompt truth, continuity state, and final claim validation separate.

Policy truth

The compiled contract: answer kind, output mode, evidence requirements, and route constraints.

Retrieval truth

The files, chunks, and search results actually found from the current project surface.

Packed prompt truth

The exact context planes that actually entered the model request after budgeting.

Continuity truth

Conversation and workflow state. Useful for routing, but not proof unless admitted as evidence.

Claim truth

The final answer must match the compiled contract and available evidence.

How the turn pipeline works

The public summary below keeps the idea high-level while preserving the private implementation boundary.

1. User turn enters the GUI or headless runtime. The same project-aware assistant concepts are available through the desktop GUI and through a private headless/eval surface.
2. Turn semantics are compiled into canonical state. The system derives policy-level intent, request type, targets, scope, and answer expectations before downstream layers act on the turn.
3. Project context and retrieval are selected. File inventory, source slices, retrieval results, summaries, and memory/context records are considered as separate forms of context rather than a single generic history.
4. Prompt/context packing consumes compiled truth. Prompt construction projects the compiled turn state and selected evidence into the model request instead of reclassifying the user request independently.
5. Tools and workflows route through deterministic layers. Command and tool execution use explicit runners, registries, planning helpers, and observation stores rather than arbitrary free-form model action.
6. Validation and post-processing check the output. The answer layer is responsible for user-facing cleanliness, route discipline, internal artifact suppression, and avoiding unsupported claims.
7. Telemetry and eval traces record what happened. Structured traces and export bundles support debugging, private headless testing, and the public RepoGrounding reports.

Key distinction: Coeus separates turn semantics, retrieval/source evidence, packed prompt context, tool execution, validation, and telemetry. This is the main architectural reason it is more than a simple model wrapper.

Release boundary

Coeus AI is currently presented as a portfolio/demo release. The public repository includes documentation, generated evaluation reports, release material, screenshots/video planning notes, and public-facing project notes.

It does not include the full private source code, private prompts, proprietary runtime internals, private traces, private provider configuration, private project data, generated caches, or the private headless runner.

A private codebase review package can be shared on request. That package contains source-tree evidence, clean local metrics, architecture and technical study notes, selected implementation evidence, screenshots, and evaluation material while excluding secrets, environment files, local traces, and build artifacts.
